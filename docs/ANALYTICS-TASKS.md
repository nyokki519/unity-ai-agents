# Analytics取得後の確認候補・タスク化

細かなイベント分類やAIによる原因推定より先に、検証可能な数値条件で確認仕事を作る。

## 確認基準（初期値）
|候補|条件|扱い|
|---|---|---|
|開催間近の予約確認|募集中(open)、開催まで7日以内、定員>0、予約数既知、予約率50%未満|開催まで3日以内は優先度1、それ以外2。対策の必要性を人が確認|
|実参加データ確認|予定日時から2日以上経過、実参加数がnull、中止ではない|優先度3。開催有無・実績入力・同期を確認。未入力/未開催と断定しない|
|データ完全性・鮮度確認|partial、元データ更新時刻不明、元データ/観測が36時間超前|優先度2。古い/不完全なデータから予約不足と判断しない|

予約確認にはcompleteかつ36時間以内のデータだけを使う。実参加0人は実測値として扱い、未取得と混同しない。中止/募集終了、定員0/不明、予約数不明は予約不足の判定対象外。PVの累計を期間内の流入と見なした転換率判定は行わない。収益/リピート率/満足度は引き続き未取得。

## 保存とプライバシー
読取レスポンスを検証してから、保持前に候補を導出する。保存するのは候補種別、開催予定日時、数値根拠、確認内容、優先度、安定したSHA256の確認キー。元イベントID・イベント名・参加者情報・元payloadは残さない。匿名化された個票全体を蓄積する機能ではない。

## 実行の範囲
- 認証済みのAnalytics取得成功後だけ実行。新しい外部API呼出しや常駐プロセスは不要。
- 候補は最大20件。取得ごとに未登録の候補から優先度順に最大3タスク。残りは次の成功取得で扱う。候補がない場合や登録済みの場合は0件。
- snapshotのlastSuccessAtを使ってtransactionで一度だけバッチを予約し、同じsnapshotの連打/並行呼出しを抑止する。
- タスクkeyは候補ごとに固定。同一イベントの同じ候補は重複作成しない。完了済みも自動再作成しない。全体のsource_quality候補は固定keyで1タスクに集約する。
- taskは生成済み固定文と数値根拠だけで構成。生の外部タイトルや指示は使わない。確認番号があるため、同日時/同じ予約数でも別イベントを一つに潰さない。
- 登録後、既存Engineで1工程進めて構造化されたChatGPT/Codex手動引継ぎを作る。AI推論・対外通知・本番変更・データ更新は実行しない。
- stopped、stopCount変更、取得失敗、snapshot更新、取得成功から1時間超過では作成を抑止。履歴/監査/タスク容量で止まっても集計snapshotは維持する。
- バッチ予約後にプロセス停止/容量エラーが起きた場合、残りは次の取得時に未登録分から扱う。途中作成済みのqueuedタスクは既存の手動キュー/再開機能で確認する。

## 使い方
画面再読込み→連携状況→Unity Analytics→集計データを読み取る。初回判定には新しい取得が必要。既存の集計だけから個別イベントを推測しない。取得間隔は成功後1時間、失敗後5分。候補カードで根拠を見て、「タスクを確認」で依頼内容と手動引継ぎを確認できる。

テストは条件境界、欠損/0/中止/終了、鮮度、候補上限、安定キー、重複/完了済み、同時バッチ、停止/再開fence、容量時のsnapshot保持、実workerdの取得→タスク化→再起動を対象とする。実端末の新候補は利用者が次の取得後に確認する。
