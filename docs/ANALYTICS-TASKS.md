# Analytics取得後の確認候補・タスク化

細かなイベント分類やAIによる原因推定より先に、検証可能な数値条件で確認仕事を作る。

## 確認基準（初期値）
|候補|条件|扱い|
|---|---|---|
|開催間近の予約確認|募集中(open)、開催まで7日以内、定員>0、予約数既知、予約率50%未満|開催まで3日以内は優先度1、それ以外2。対策の必要性を人が確認|
|実参加データ確認|予定日時から2日以上経過、実参加数がnull、中止ではない|優先度3。開催有無・実績入力・同期を確認。未入力/未開催と断定しない|
|データ完全性・鮮度確認|partial、元データ更新時刻不明、元データ/観測が36時間超前|優先度2。古い/不完全なデータから予約不足と判断しない|

予約確認にはcompleteかつ36時間以内のデータだけを使う。実参加0人は実測値として扱い、未取得と混同しない。中止/募集終了、定員0/不明、予約数不明は予約不足の判定対象外。PVの累計を期間内の流入と見なした転換率判定は行わない。収益/リピート率/満足度は引き続き未取得。

## 保存とプライバシー
読取レスポンスを検証してから、保持前に候補を導出する。保存するのは候補種別、開催予定日時、数値根拠、確認内容、優先度、安定したSHA256の確認キー。元イベントID・イベント名・参加者情報・元payloadは残さない。匿名化された個票全体を蓄積する機能ではない。

## 実行の範囲
- 認証済みのAnalytics取得成功後だけ実行。新しい外部API呼出しや常駐プロセスは不要。
- 候補は最大20件。取得ごとに未登録の候補から優先度順に最大3タスク。残りは次の成功取得で扱う。候補がない場合や登録済みの場合は0件。
- snapshotのlastSuccessAtを使ってtransactionで一度だけバッチを予約し、同じsnapshotの連打/並行呼出しを抑止する。
- タスクkeyは候補ごとに固定。同一イベントの同じ候補は重複作成しない。完了済みも自動再作成しない。全体のsource_quality候補は固定keyで1タスクに集約する。
- taskは生成済み固定文と数値根拠だけで構成。生の外部タイトルや指示は使わない。確認番号があるため、同日時/同じ予約数でも別イベントを一つに潰さない。
- 登録後、既存Engineで1工程進めて構造化されたChatGPT/Codex手動引継ぎを作る。AI推論・対外通知・本番変更・データ更新は実行しない。
- stopped、stopCount変更、取得失敗、snapshot更新、取得成功から1時間超過では作成を抑止。履歴/監査/タスク容量で止まっても集計snapshotは維持する。
- バッチ予約後にプロセス停止/容量エラーが起きた場合、残りは次の取得時に未登録分から扱う。途中作成済みのqueuedタスクは既存の手動キュー/再開機能で確認する。

## 使い方
画面再読込み→連携状況→Unity Analytics→集計データを読み取る。初回判定には新しい取得が必要。既存の集計だけから個別イベントを推測しない。取得間隔は成功後1時間、失敗後5分。候補カードで根拠を見て、「タスクを確認」で依頼内容と手動引継ぎを確認できる。

テストは条件境界、欠損/0/中止/終了、鮮度、候補上限、安定キー、重複/完了済み、同時バッチ、停止/再開fence、容量時のsnapshot保持、実workerdの取得→タスク化→再起動を対象とする。実端末の新候補は利用者が次の取得後に確認する。

## 具体的な確認手順
「タスク」内の「確認手順・完了条件」を開くと、候補別の手順と記録すべき結果を表示する。予約確認は予約数・定員・申込導線・告知状況・次回確認日時、実参加確認は開催有無・実績記録・同期、鮮度確認は同期履歴・対象期間・判断を保留する指標を整理する。

新規タスクには手順を依頼本文にも含める。既存タスクは現在の確認候補とキーが一致する場合に表示だけを追加し、保存済みの依頼内容は変更しない。現在の候補から外れた旧タスクには追加表示しない。分からない情報は「未確認」と記録し、原因や人数を推測しない。完了条件は人の確認用であり、自動検証・自動改善実行ではない。

## 確認結果の記録
引継ぎ待ちのタスクは、日本語フォームで要約・根拠・反論/注意点・未確認事項・次回確認予定を入力できる。根拠などは1行1件、最大8件、各2000文字。次回確認を入力した場合は未確認事項を7件までとし、8件目に予定を保存する。既存の結果schema/APIを使い、保存状態の移行は不要。JSONによる入力も詳細操作に残している。

次回確認は「予定・未検証」のメモであり、自動予約・通知・担当者への依頼ではない。結果はタスク内に表示し、実行計画内の既存結果も表示できる。保存だけでは施策の効果を認定せず、既存Engineの次工程待ちへ進める。保存内容は自己申告であり自動的な事実検証はしない。参加者情報・秘密値は入力しない。

UI回帰確認: `npm run build` 後、PythonのPlaywrightとChromiumを用意し、repo直下で `python scripts/result-form-smoke.py`。必要に応じ `CHROMIUM_PATH` で実行ファイルを指定する。模擬タスク/一時保存だけを使い、上限エラーでの入力保持、保存/再ログイン後の表示、次工程待ち、390px表示を検証する。

## 集客確認の依頼テンプレート
「タスク」→「集客確認テンプレートを入れる」で、イベント情報・募集状態・定員/予約数/残席・確認日時/参照元・告知先/掲載日時・申込導線・類似イベント・作業時間・次回確認を入力できる。入力中の依頼は上書きしない。分かる項目だけ未確認から書き換え、通常の「指示を登録」を使う。

同じ開催前日数/定義/母数での比較、最大3案への絞込み、完了条件/期待効果/難易度/費用/リスクの整理を手動AI引継ぎへ依頼する。これは入力ひな形であり、自動分析・イベント情報の自動補完・サイト点検・告知変更ではない。リンクはデータとして扱い、自動アクセスしない。追加金銭費用0円、AI推論は引き続きChatGPT/Codexへの手動引継ぎ。未確認の数値/因果/収益などを捏造しない。

UI回帰: `npm run build` 後 `python scripts/marketing-template-smoke.py`（Python Playwright/Chromium、必要ならCHROMIUM_PATH）。入力保護・ひな形編集・Marketing引継ぎ・追加外部呼出し0を模擬タスクで確認する。

## 取得済みデータの自動添付
引継ぎ待ちのMarketingタスクには、保存済みAnalyticsの取得/観測/元データ更新日時、対象期間、全体の予約・実参加・PVと既知/対象イベント数を自動添付する。個別イベントが特定できなければ全体集計のみ。全体予約数を特定イベントの予約数として使わない。

予約確認候補は `analytics-finding-<候補key>` が一致する場合だけ、開催予定日時と候補検出時の根拠を追加する。同じ日時や似た数値で他イベントと対応付けない。既存の待機中タスクには表示する引継ぎの補足として追加し、保存済み依頼/計画/結果は変更しない。新規の予約確認タスクには作成時点の参照情報と集客検討依頼も保存する。タスク数上限・重複防止・停止fenceは従来通り。

取得失敗、部分同期、36時間超、取得/観測/元更新時刻の不明/未来は判断保留。数値は過去の参照値としてのみ扱う。古い候補の根拠も検出時点の記録と明記する。告知履歴、申込導線、過去比較、担当/次回日時、収益/リピート/満足度は自動補完しない。添付による外部API呼出しは0。AI推論の手動引継ぎは引き続き必要。

## 無人の日次監視
Cloudflare Cronから毎日07:40（日本時間）に取得→判定→最大3件の内部確認タスク作成を実行する。ブラウザ操作/常時端末は不要。設定済みの専用キーを再利用する。緊急停止・キー未設定は通信しない。最後の実行日時・結果・作成件数はダッシュボード「自動監視」へ表示。

JSTの同日claimを永続化し、配信重複/再起動でも再実行しない。失敗日は自動再試行せず、次の日の定期実行または既存の手動取得を使う。処理中に中断した場合は「実行中・未完了」が残り、完了と偽らない。過去日の自動取得履歴を一覧保存する機能はなく、最新1回のみ（作成されたタスク/工程履歴は従来通り保持）。Cronは遅延し得る。

公開URLでは内部起動用パスへルーティングしない。Worker→同一DO内の起動だけを許し、既存管理者のBearer認証・固定Origin・Free設定も検証する。AI推論・外部送付・本番変更・全キュー実行はしない。無料条件が変われば停止して再確認する。

## 前回の成功取得との比較
取得成功時に前回の集計を1回分だけ保持する（候補の自由文は複製しない）。現データが失敗・部分・古い/時刻不明なら差分を判断に使わない。前回は観測時点で36h以内の元データを使っていること、観測順が正しいこと、7日以内の観測であることを確認する。

比較には指標ごとのSHA256照合値を使う。固定source/schema/指標定義、非中止の対象イベントID・正規化した開催日時・値の取得有無から作り、元IDは保存しない。イベント件数や既知件数が等しくても対象が違えば比較しない。実参加の対象は過去イベントのみなので、新たに過去へ移ったイベントがあれば比較不可となる。旧保存データに照合値がなければ比較待ち。通常は更新後2回の成功取得で比較できるようになる。

ダッシュボードに観測日時と時点合計の差分を表示する。ゼロは実測、nullは未取得。前回の取得失敗では保存済みの成功データ/比較元を上書きしない。比較不可の前回値はAIにも渡さず、理由とnullを送る。比較できる差分だけ無料AIの投影へ追加し、追加のAPI/推論は呼ばない。差分は施策の因果や期間流入/転換率ではない。対象期間が動いても同じイベント群の時点値として比較し、期間集計として扱わない。

## 自動運転の実行診断
クラウド管理画面の取得時に、保存済みの定期処理/AI記録だけを調べる。初回記録なしは確認待ち、最終開始から36h超は遅延、実行中が2分超残れば未完了として表示する。停止中は意図した停止を優先表示し、予定障害と断定しない。部分完了・キー不足・取得間隔による見送り・未来/逆転時刻・不整合な完了記録も区別する。

AI生成失敗は、安全な理由コードに応じてJSON形式・25秒timeout・無料枠/接続確認の手順を固定文で示す。根本原因を特定したと偽らない。AI後にデータが更新された場合は、次の分析待ちとして扱う。「完了記録あり」は保存記録についてだけで、提案の正しさや全サービス正常の保証ではない。

診断は読み取りのみ。追加API/AI、強制retry、キー変更、外部通知は行わない。初回の実行記録が全くない場合は、予定開始日が記録されていないため「初回待ち」のまま。初回の取りこぼし時刻やアカウントの残枠までは判定できない。通知のpushではなく、画面を開いた際に表示する。

## 日次運営サマリー
管理画面を開いた時点で、保存済みの集計・条件付き比較・確認候補・タスク状態を短いサマリーへ再構成する。事実、固定ルールの確認事項、未検証AIの要約を別表示。追加の外部API/推論/タスク作成は行わない。

古い/部分/取得失敗等の値は数値の事実欄から除き、確認を保留する。nullを0としない。開催済みになった予約候補は集客確認から外す。AIの要約は成功・鮮度・参照データ一致を満たす場合だけ別欄に表示する。合計は取得できたイベント群の値であり、施策効果や個別イベントの値とは扱わない。

「運営サマリーを保存（Markdown）」は端末へのダウンロードだけ。モデル文章・候補自由文・元IDは含めず、事実と固定の確認事項だけを書き出す。外部送付・公開・日次履歴の自動保存ではない。観測日時と表示用生成日時を区別する。
